одной пачкой, findings записывай по правилам ниже.
Формат таблицы:

| Модуль | Файл:строка | Категория | Проблема | Severity | Confidence | Как исправить |
|--------|-------------|-----------|----------|----------|------------|---------------|

Severity: BLOCKER / MAJOR / MINOR.
Confidence: HIGH (код прочитан в этой сессии) / MEDIUM (косвенные
признаки) / LOW (эвристика или не подтверждено).

## ПРАВИЛО: запись findings после каждого turn

Если при чтении файлов нашёл проблему — сразу сохраняй findings через
`update_work_state` (`{"findings+": [...]}`), не откладывай до конца аудита.
НЕ батчи findings на конец аудита: несколько файлов читай одним вызовом
`read_files`; записывай findings один раз на пачку прочитанных файлов, до
начала следующей пачки. Один файл, прочитанный через `read_file`, тоже
считается отдельной пачкой.

При compress незаписанные findings теряются, и их приходится искать заново —
это дороже по токенам и хуже по полноте (сессия f0fbbe9a: 3 compress,
work_state пуст до явной просьбы, +1.82₽ на повтор).

## ПРАВИЛА ПРИМЕНИМОСТИ ПРОВЕРОК

Следующие проверки и эвристики запускай только когда scope/прочитанный код
содержит соответствующую технологию или паттерн. Не ищи SQL race в проекте без
БД, не проверяй импорты вне целевого сценария и не сканируй все файлы в поисках
каждой эвристики. Если паттерн есть, проверь его в релевантном пути; если нет —
пометь категорию «не применимо».

1. **Bounded reading.** Не читай файл целиком, если он >200 строк.
   `read_file(limit=30)` → docstring + импорты. Тело функции —
   `read_file(offset=N, limit=30)`. НЕ используй `list_files` на весь
   проект (возвращает 12KB, раздувает контекст, ломает prefix cache):
   `run_command('find <путь> -name "*.py" -type f -maxdepth 2')`.
   (Порядок опций в run_command строгий: `-name` → `-type` → `-maxdepth`;
   `-not`, `-exec`, `-delete` запрещены. `__init__.py` пропускай глазами.)
   Батчинг: прочитал 5 файлов → одна запись findings на все 5.

2. **Import-check — по релевантности.** Проверяй импорты, которые влияют
   на целевой сценарий, изменённый модуль или конкретный finding; не делай
   инвентаризацию каждого импорта в узком аудите. Если релевантный импорт
   отсутствует или молча отключает функциональность через fallback, подтверди
   это и оцени impact как finding.

3. **SQL-транзакции и race.** Видишь `SELECT ... WHERE overlap` затем
   `INSERT`/`UPDATE` в одной функции — проверь, открыта ли транзакция
   (`BEGIN IMMEDIATE` / `isolation_level`) ДО SELECT. `aiosqlite` по
   умолчанию autocommit → SELECT и INSERT не атомарны, двойное
   бронирование возможно. `executescript()` делает implicit COMMIT
   открытой транзакции — проверь, не ломает ли это атомарность
   миграций (`init_db` → `rollback` после `executescript` не откатит).

4. **hasattr(X, 'attr') vs реальный `_attr`.** Если код проверяет
   `hasattr(obj, 'name')`, но у класса атрибут называется `_name` (с
   подчёркиванием) — это **MAJOR**: hasattr всегда False → ветка не
   выполняется молча. Проверка: `grep 'self._name\|self.name' <class>.py`.
   Пример: `hasattr(self.e, 'strategies')`, а у CarryEngine `_strategies` →
   цены 0.0, все стопы молчат.

5. **Silent failure — конкретные паттерны.** Грепай явно:
   `except: pass`, `except Exception: pass`,
   `except Exception as e: log.debug(...)` без `return`/`raise`,
   `except ImportError: logger.debug(...); return <default>`,
   `getattr(module, attr)` без валидации. Голый `except` в критичных
   путях (удаление, миграции, деньги) — MAJOR; в UI-fallback — MINOR.

## 1.2. Логика и бизнес-правила
Для каждого ключевого сценария:
| Сценарий | Файл | Зарегистрирован? | Вызывается? | Вход | Выход | Состояние | Замечания |

Проверь:
- Где регистрируется/вызывается сценарий.
- Реально ли он используется или лежит мёртвым грузом.
- **Dead params.** Функция объявляет параметр, но тело его не использует
  (`nights`, `timeout`, `retries`, `room_id`) — MAJOR, если параметр влияет
  на деньги/поведение, MINOR если косметика. Проверка: grep каждого имени
  параметра в теле функции; 1 совпадение (только в сигнатуре) = dead param.
  Пример: `calculate_guests_surcharge(nights)` — `surcharge += count * price`
  без `* nights`, недоплата ×N ночей, `extra_text` пишет «{price}₽/ночь»,
  а сумма — за 1 ночь.
- Есть ли условия входа и выхода.
- Обрабатываются ли: нет данных, мало данных, NaN/None, ошибка.
- Сохраняется ли состояние между перезапусками.
- Совпадает ли реализация с названием/docstring/комментариями.
- Есть ли silent fail: неверный фильтр, ошибка регистрации, проглоченное исключение.
- Конфликты: два правила дают противоположный результат — как решается.
