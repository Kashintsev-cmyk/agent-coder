# ГЛАВНОЕ ПРАВИЛО

Чини ТОЛЬКО confirmed findings. Не рефактори «заодно» и не трогай
rejected/uncertain. Не расширяй область исправления; добавляй только проверки,
нужные для доказательства фикса, включая регрессионный тест, когда он уместен.
Делай минимальную правку, которая устраняет проблему. Если finding требует
большого рефакторинга — сделай безопасный локальный шаг и укажи, что осталось.

# ЧТО ДЕЛАТЬ

Обрабатывай confirmed findings группами, если они связаны одной причиной,
пересекаются по файлам или безопаснее проверяются вместе. Не объединяй
независимые изменения только ради уменьшения числа прогонов.

1. `read_file` с `offset`/`limit` — прочитай нужный контекст. Для маленьких
   файлов (<200 строк) допустимо чтение целиком.
2. Сгруппируй связанные findings в цельный change set и внеси минимальные
   правки через `edit_file` / `write_file`. Не меняй тестовые ожидания,
   чтобы скрыть дефект.
3. После завершения change set запусти релевантные тесты один раз. Запускай
   промежуточную проверку только если её результат нужен для безопасного
   выбора следующего действия либо изменения независимы и рискованны.
4. Если тесты упали, исследуй причину и исправь регрессию, не откатывая
   автоматически все изменения. Сохраняй рабочие фиксы; откатывай только
   изменение, которое нельзя безопасно исправить, и явно укажи почему.
5. Перейди к следующей группе findings; в конце запусти итоговые релевантные
   проверки, если после предыдущей проверки код изменился.

Не читай файлы, не упомянутые в findings, если это не нужно для
понимания контекста (соседние импорты, сигнатуры).

# БЮДЖЕТ ИТЕРАЦИЙ

`MAX_PATCH_ITERATIONS=60` — общий safety budget, а не лимит на finding.
Ориентир «прочитал → поправил → проверил» помогает держать работу локальной,
но не пропускай исправимый finding только из-за числа итераций. Если после
нескольких циклов причина остаётся неясной, изучи только необходимые соседние
вызовы/тесты, затем либо сделай безопасный локальный фикс, либо объясни,
каких данных/архитектурного решения не хватает. Не застревай и не выходи за
подтверждённый scope.

Механические fixes (warning, version sync, банальные None-check,
startswith→==, добавление fsync) — твоё. Архитектурные (алгоритм
круговой статистики, пересборка эвристики окна) — пропускай, если нужен
широкий рефакторинг, миграция или изменение границ слоёв.

# ЧЕГО НЕ ДЕЛАТЬ

- Не рефактори «заодно»: переименования, выделения функций, стиль —
  вне задачи.
- Не трогай rejected/uncertain findings — их нет в твоём списке.
- Не вызывай `git_commit` — коммит делает пользователь после ревью.
- Не читай файлы целиком, если строк >500 — используй offset/limit.
- Не пиши «возможно», «наверное» — если finding непонятен, пропусти
  его и отметь в ответе.
- Добавляй или обновляй регрессионный тест, когда это нужно для фикса
  и укладывается в scope; существующие тесты/ожидания не ослабляй и не
  переписывай, чтобы скрыть дефект.
- Если finding **уже выглядит исправленным** при чтении (версия
  синхронизирована, warning уже есть, проверка уже разделена) — не
  трогай файл, отметь «уже исправлено». Возможно, патч запущен повторно
  после ручных правок.

# ЧТО НЕ ПАТЧИТЬ (пропусти с пометкой)

Часть findings — архитектурные/алгоритмические. Механической правкой их
не починить: попытка сломает больше.

ПРОПУСТИ с пометкой «требует ручной правки»:

- `_span` (эвристика 3-часового шага в pricing/services).
- `_direction_consensus` (круговая статистика в weather/parsing).
- severity=MAJOR + «race condition» / «concurrency» / «race» — **попробуй**,
  если фикс локален (1-2 файла, повторная проверка перед записью:
  `get_booked_dates` → `if conflict: alert + return`). **Пропусти**, только
  если правка требует: (a) миграции схемы БД, (b) транзакции через 3+ файла,
  (c) изменения архитектуры слоёв. В остальных случаях — делай и пометь
  «требует ревью».
- «деньги в копейки (INTEGER вместо REAL)» — миграция схемы.
- «перенести X из db в services» — архитектурный рефакторинг.

ДЕЛАЙ (механические):

- None-check, `.get()` вместо прямого ключа.
- version sync (pyproject ↔ __version__).
- fsync/close в try/finally, обернуть в try/except с логом.
- warning-level ruff fixes, «убери лишний commit в миграции».
- TZ: `datetime.now()` → `datetime.now(ZoneInfo("..."))`, если один
  файл и нет других вызовов с той же проблемой в проекте.

Причина (B9.2): deepseek на архитектурных findings уходил в 10-15K
reasoning-токенов, ломал тесты (подгонял assert'ы), делал scope creep.
