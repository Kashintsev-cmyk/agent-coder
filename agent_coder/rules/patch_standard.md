сделай минимальный шаг и отметь в ответе, что осталось.

# ЧТО ДЕЛАТЬ

Для каждого confirmed finding:

1. `read_file` с `offset`/`limit` — прочитай только нужный кусок, не
   весь файл. Для маленьких (<200 строк) — целиком.
2. `edit_file` (точечная правка) или `write_file` (если файл <30 строк
   или правка >50% файла).
3. `run_command` — прогони тесты СРАЗУ после `edit_file`/`write_file`,
   если они есть (`pytest -q` или как в README проекта). Если твоя
   правка сломала тесты — **немедленно откати её** через `edit_file`
   обратно (или `write_file` исходным содержимым) и отметь finding
   как «не удалось, требуется ручная правка». Не оставляй сломанное.
4. Переходи к следующему finding.

Не читай файлы, не упомянутые в findings, если это не нужно для
понимания контекста (соседние импорты, сигнатуры).

# БЮДЖЕТ ИТЕРАЦИЙ

Ты работаешь в цикле (MAX_PATCH_ITERATIONS=60). На каждый finding —
**не больше 2-3 итераций**: прочитал → поправил → тесты. Если после
2 итераций чтения ты ещё не правишь файл — **это сложный finding**.
Не пытайся решить его «в голове» — пропусти с пометкой в отчёте:

```
Осталось: finding <N> (<файл>) — требует ручной правки (сложная логика).
```

**Лучше 5 маленьких правок, чем 0 на 5 сложных.** Не застревай.
Механические fixes (warning, version sync, банальные None-check,
startswith→==, добавление fsync) — твоё. Архитектурные (алгоритм
круговой статистики, пересборка эвристики окна) — пропускай.

# ЧЕГО НЕ ДЕЛАТЬ

- Не рефактори «заодно»: переименования, выделения функций, стиль —
  вне задачи.
- Не трогай rejected/uncertain findings — их нет в твоём списке.
- Не вызывай `git_commit` — коммит делает пользователь после ревью.
- Не читай файлы целиком, если строк >500 — используй offset/limit.
- Не пиши «возможно», «наверное» — если finding непонятен, пропусти
  его и отметь в ответе.
- Не добавляй тесты, которых не было, если finding не про «нет тестов».
- Если finding **уже выглядит исправленным** при чтении (версия
  синхронизирована, warning уже есть, проверка уже разделена) — не
  трогай файл, отметь «уже исправлено». Возможно, патч запущен повторно
  после ручных правок.

# ЧТО НЕ ПАТЧИТЬ (пропусти с пометкой)

Часть findings — архитектурные/алгоритмические. Механической правкой их
не починить: попытка сломает больше.

ПРОПУСТИ с пометкой «требует ручной правки»:

- `_span` (эвристика 3-часового шага в pricing/services).
- `_direction_consensus` (круговая статистика в weather/parsing).
- severity=MAJOR + «race condition» / «concurrency» / «race» — **попробуй**,
  если фикс локален (1-2 файла, повторная проверка перед записью:
  `get_booked_dates` → `if conflict: alert + return`). **Пропусти**, только
  если правка требует: (a) миграции схемы БД, (b) транзакции через 3+ файла,
  (c) изменения архитектуры слоёв. В остальных случаях — делай и пометь
  «требует ревью».
- «деньги в копейки (INTEGER вместо REAL)» — миграция схемы.
- «перенести X из db в services» — архитектурный рефакторинг.

ДЕЛАЙ (механические):

- None-check, `.get()` вместо прямого ключа.
- version sync (pyproject ↔ __version__).
- fsync/close в try/finally, обернуть в try/except с логом.
- warning-level ruff fixes, «убери лишний commit в миграции».
- TZ: `datetime.now()` → `datetime.now(ZoneInfo("..."))`, если один
  файл и нет других вызовов с той же проблемой в проекте.

Причина (B9.2): deepseek на архитектурных findings уходил в 10-15K
reasoning-токенов, ломал тесты (подгонял assert'ы), делал scope creep.
