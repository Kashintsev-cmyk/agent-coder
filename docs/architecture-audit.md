## Источники истины и найденные границы

- `Mode` централизован как enum. `ModePolicy` пока не вводить: сначала доказать конкретное дублирование.
- `ToolStatus`/`ToolExecutionResult` существуют. `read_file`, `list_files`, `search` и `run_checks` возвращают структурированный результат; их `_execute` оставлен как совместимая обёртка над `_execute_result`. Legacy-строки других инструментов по-прежнему классифицируются эвристикой по тексту (`normalize_tool_result`).
- Read-only означает разрешённость инструмента, а не успешность конкретного вызова.
- Статус вызова и прогресс задачи — разные понятия. Ошибочные ответы `read_file` («Файл не найден», «уже прочитан») теперь имеют явный статус ERROR/REJECTED и не классифицируются как успех.
- Обработка результата распределена между loop, patch и verify; `normalize_tool_result` вызывается в каждом из них (`loop.py:791`, `patch.py:420`, `verify.py:309`). Safe-call: единственный источник — `run_command._is_safe_command` (`run_command.py:870`), проверка в `Tool.needs_approval` и `ToolRegistry.is_call_allowed`; дублирующей логики не найдено.
- Benchmark: `tool_calls` считает вызовы основного transcript, не patch/verify; это следует обозначать как границу метрики.

## Лимиты и продолжение задач

- Audit: 200 итераций на волну и до 3 автопродолжений — намеренный предел до 800 итераций.
- `MAX_COST_PER_TASK` и watchdog-счётчики локальны для `loop.run()` и сбрасываются между волнами.
- Lifecycle задачи реализован: новый запрос вызывает `session.begin_task()` (новый id, сброс watchdog); продолжение (`continuation`) берёт существующий `task_state`; `started_cost` сохраняет бюджет задачи между волнами; отмена вызывает `session.end_task()`; `total_usage` сессии общий.
- Telegram-кнопка продолжения привязана к id задачи (`continue_task:<session_id>:<task_id>`), проверка в `cb_continue_task` (`task.py:270`).
- README лимиты согласованы с `config.py` и `.env.example` (100/200/200; `MAX_AUTO_CONTINUE=3`). Устаревших 30/50/100 в README не найдено.

## Цель и критерии готовности

Цель: проект соответствует индустриальному стандарту по архитектуре, тестам и CI.
Каждая задача выполняется с первого прохода: одна понятная правка, один целевой тест,
без повторных чтений файлов и без лишних запросов к LLM. Качество измеряется
количеством закрытых контрактов с тестами, а не объёмом переписанного кода.

Критерии готовности (все должны выполняться):
- Один источник истины на каждый режим (PLAN/ACT/AUDIT): правила режима
  (набор инструментов, лимиты, промпт, политика approval) задаются в ядре
  (`agent_coder/agent/`, `agent_coder/tools/registry.py`), а не в адаптерах.
  Адаптеры (CLI, Telegram) только вызывают ядро. Перед введением `ModePolicy`
  нужно доказать конкретное дублирование тестом или grep-ом.
- Все инструменты возвращают `ToolExecutionResult`; `normalize_tool_result`
  остаётся только как совместимость для внешних инструментов и покрыт тестами.
- Один контракт safe-call (`run_command._is_safe_command`), без дублей в
  loop/patch/verify.
- Lifecycle задачи покрыт тестами: новый запрос, продолжение, отмена, бюджет
  между волнами, привязка кнопки к id задачи.
- README и benchmark/README соответствуют runtime-конфигурации.
- Полный CI-gate зелёный: `ruff check .`, `ruff format --check .`, `mypy`,
  `bandit -r agent_coder -c bandit.yaml`, `pytest -q -n auto`.
